# Debian Static IP Configuration

## Overview

This document provides a general reference for configuring a static IPv4 address on Debian Linux.

Debian systems may use different networking frameworks depending on the installation method, system role, and installed packages. Before changing network configuration, identify which networking framework currently manages the interface.

Common implementations include:

- `ifupdown`
- `systemd-networkd`
- NetworkManager

Resolver management may also vary between installations. DNS configuration should therefore be explicitly validated after changing network settings.

> [!Important]
> Do not modify the interface currently providing remote SSH connectivity unless console or alternate management access is available. An incorrect network configuration can immediately disconnect the system.


## Example Network Configuration

The examples in this document use placeholder addressing:

| Setting | Example |
|---|---|
| Interface | `ens18` |
| IPv4 Address | `10.0.0.50` |
| Prefix | `/24` |
| Default Gateway | `10.0.0.1` |
| Primary DNS | `10.0.0.10` |
| Secondary DNS | `10.0.0.11` |
| DNS Domain | `lab.example.com` |

Replace these values with those appropriate for the deployed environment.


## Identify the Network Interface

Display available interfaces and current addresses:

```bash
ip -br addr
```

Example:

```text
lo       UNKNOWN        127.0.0.1/8
ens18    UP             10.0.0.150/24
```

Display routing information:

```bash
ip route
```

The interface associated with the default route is typically the primary network interface.


## Identify the Networking Framework

### Check NetworkManager

```bash
systemctl is-active NetworkManager
```

### Check systemd-networkd

```bash
systemctl is-active systemd-networkd
```

### Check ifupdown

Inspect:

```bash
cat /etc/network/interfaces
```

and:

```bash
ls -la /etc/network/interfaces.d/
```

A configuration such as:

```text
allow-hotplug ens18
iface ens18 inet dhcp
```

indicates that the interface is configured through traditional Debian `ifupdown`.

Use the configuration method corresponding to the framework managing the interface.


# ifupdown

## Current DHCP Configuration

A DHCP-configured interface may appear in `/etc/network/interfaces` as:

```text
allow-hotplug ens18
iface ens18 inet dhcp
```

Back up the existing configuration before making changes:

```bash
sudo cp /etc/network/interfaces /etc/network/interfaces.backup
```

Edit the configuration:

```bash
sudo vi /etc/network/interfaces
```

Change the interface from DHCP to static addressing:

```text
allow-hotplug ens18
iface ens18 inet static
    address 10.0.0.50/24
    gateway 10.0.0.1
    dns-nameservers 10.0.0.10 10.0.0.11
    dns-search lab.example.com
```


## DNS Resolver Integration

When using `ifupdown`, the `dns-nameservers` and `dns-search` directives require resolver integration to update `/etc/resolv.conf`.

On systems using the `resolvconf` implementation, verify whether the package is installed:

```bash
dpkg -s resolvconf >/dev/null 2>&1 && echo "resolvconf installed" || echo "resolvconf not installed"
```

If required and not installed:

```bash
sudo apt update
sudo apt install resolvconf
```

After installation, `/etc/resolv.conf` is normally managed dynamically by `resolvconf` and should not be edited directly.

Verify:

```bash
ls -l /etc/resolv.conf
cat /etc/resolv.conf
```

A generated resolver configuration may resemble:

```text
# Dynamic resolv.conf generated by resolvconf
nameserver 10.0.0.10
nameserver 10.0.0.11
search lab.example.com
```

> [!Important]
> The presence of `dns-nameservers` and `dns-search` in `/etc/network/interfaces` does not by itself guarantee that `/etc/resolv.conf` contains usable resolver information. Always validate DNS after applying the static configuration.

> [!Note]
> `resolvconf` is not required on every Debian installation. Resolver management depends on the networking stack and installed components. Systems managed by NetworkManager or `systemd-networkd` may use different resolver integration and should be configured using their respective mechanisms.

If DNS is already unavailable and the system must access package repositories to install resolver integration, temporary resolver information may be placed in `/etc/resolv.conf`:

```text
search lab.example.com
nameserver 10.0.0.10
nameserver 10.0.0.11
```

Verify DNS resolution before attempting package installation:

```bash
getent hosts example.com
```

After the resolver-management package is installed and the network configuration is reapplied or the system is rebooted, verify that `/etc/resolv.conf` is being generated correctly rather than relying on the temporary configuration.


## Apply the Configuration

Apply the configuration:

```bash
sudo ifdown ens18
sudo ifup ens18
```

> [!Warning]
> Running `ifdown` on an interface being used for SSH will interrupt the connection. Use local or hypervisor console access when possible.

> [!Note]
> When changing an active interface from DHCP to static, the old DHCP address or routes may remain temporarily. Verify with `ip -br addr` and `ip route`. If they remain, a planned reboot provides a clean network restart.

A reboot may also be used during a planned maintenance window:

```bash
sudo reboot
```


# systemd-networkd

Create or edit the appropriate `.network` file:

```bash
sudo vi /etc/systemd/network/20-wired.network
```

Example:

```ini
[Match]
Name=ens18

[Network]
Address=10.0.0.50/24
Gateway=10.0.0.1
DNS=10.0.0.10
DNS=10.0.0.11
Domains=lab.example.com
```

Restart the networking service:

```bash
sudo systemctl restart systemd-networkd
```


# NetworkManager

List connections:

```bash
nmcli connection show
```

Identify the connection associated with the target interface.

Configure static IPv4 addressing:

```bash
sudo nmcli connection modify "Wired connection 1" \
    ipv4.method manual \
    ipv4.addresses 10.0.0.50/24 \
    ipv4.gateway 10.0.0.1 \
    ipv4.dns "10.0.0.10 10.0.0.11" \
    ipv4.dns-search "lab.example.com"
```

Apply the configuration:

```bash
sudo nmcli connection up "Wired connection 1"
```


# Validation

## Verify Address

```bash
ip -br addr
```

Confirm the expected static IPv4 address is assigned.


## Verify Default Route

```bash
ip route
```

Expected structure:

```text
default via 10.0.0.1 dev ens18
10.0.0.0/24 dev ens18 proto kernel scope link
```


## Verify Gateway Connectivity

```bash
ping -c 4 10.0.0.1
```


## Verify DNS Configuration

Depending on the resolver configuration:

```bash
cat /etc/resolv.conf
```

or:

```bash
resolvectl status
```

Confirm that the expected DNS servers and, when applicable, DNS search domain are present.

For example:

```text
nameserver 10.0.0.10
nameserver 10.0.0.11
search lab.example.com
```

A configured static IP and working default route do not prove that DNS is correctly configured.


## Verify DNS Resolution

Test external DNS resolution:

```bash
getent hosts example.com
```

If internal DNS is deployed, test an appropriate fully qualified hostname:

```bash
getent hosts server01.lab.example.com
```

If a DNS search domain is configured, optionally verify short-name resolution:

```bash
getent hosts server01
```


## Verify Internet Connectivity

Test connectivity without relying on DNS:

```bash
ping -c 4 1.1.1.1
```

Then test DNS-dependent connectivity:

```bash
ping -c 4 example.com
```

Successful IP connectivity combined with failed hostname resolution generally indicates a DNS or resolver-configuration problem rather than a routing problem.


## Verify Time Synchronization

DNS problems may also prevent services that depend on hostname resolution from operating correctly, including network time synchronization.

Check time synchronization:

```bash
timedatectl
```

Expected status:

```text
System clock synchronized: yes
NTP service: active
```

Additional synchronization details can be displayed with:

```bash
timedatectl timesync-status
```

If the NTP service is active but no server is selected or no packets have been exchanged, verify DNS resolution before changing the NTP configuration.


# Operational Considerations

Static addresses should generally be assigned to infrastructure that must remain predictably reachable, such as:

- Hypervisors
- DNS and directory servers
- Network infrastructure
- Storage systems
- Management systems
- Selected infrastructure services

Client endpoints are generally better suited to DHCP.

Static addresses should be selected from address space intentionally reserved for static infrastructure and should not overlap with active DHCP allocation ranges.

Maintain assignments in network documentation or an IP address management system to prevent duplicate addresses.


## Recovery

If a static configuration prevents network connectivity, access the system through its local or hypervisor console.

For `ifupdown`, restore the previous configuration:

```bash
sudo cp /etc/network/interfaces.backup /etc/network/interfaces
```

Then reboot or restart the affected networking configuration.

If IP connectivity works but DNS does not, inspect the resolver configuration:

```bash
cat /etc/resolv.conf
```

Test the configured DNS server directly when appropriate:

```bash
nslookup example.com 10.0.0.10
```

If the direct query succeeds while normal hostname resolution fails, investigate the local resolver configuration rather than routing or the upstream DNS server.


## Security and Documentation

Public documentation should not expose production or private-environment addressing plans, hostnames, DNS domains, interface identifiers unique to a system, credentials, or other environment-specific identifiers.

Use generalized examples such as:

```text
10.0.0.0/24
lab.example.com
server01
```

and maintain actual deployment values in private infrastructure documentation.
