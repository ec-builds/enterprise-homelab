# Log Rotation / logrotate

## Overview

`logrotate` manages the rotation, compression, retention, and removal of log files on Linux systems.

In the homelab, the host operating system uses `logrotate` to manage persistent logs generated by containerized services.

The current implementation is used with the centralized rsyslog collector to:

- Rotate active logs daily
- Use date-based filenames
- Compress historical logs
- Maintain approximately 90 days of local history
- Prevent active log files from growing indefinitely
- Rotate logs without restarting the rsyslog container

>[!note]
>`logrotate` operates on the host rather than inside the rsyslog container.

## Quick Reference

| Task | Command |
|---|---|
| Check logrotate version | `logrotate --version` |
| Test configuration without rotating | `sudo logrotate -d /etc/logrotate.d/<CONFIG>` |
| Force rotation | `sudo logrotate -f /etc/logrotate.d/<CONFIG>` |
| Force rotation with verbose output | `sudo logrotate -vf /etc/logrotate.d/<CONFIG>` |
| Check automatic rotation timer | `systemctl status logrotate.timer` |
| Show next scheduled rotation | `systemctl list-timers logrotate.timer` |
| Check logrotate service | `systemctl status logrotate.service` |
| View recent service logs | `journalctl -u logrotate.service` |
| List active and rotated logs | `ls -lh <LOG-DIRECTORY>` |
| Read compressed log | `zless <LOG-FILE>.gz` |
| Search compressed log | `zgrep "<PATTERN>" <LOG-FILE>.gz` |

## How logrotate Works

`logrotate` periodically evaluates configured log files and determines whether they meet their rotation criteria.

A typical lifecycle is:

    Active Log
        │
        ▼
    Rotation Trigger
        │
        ▼
    Rotated Log
        │
        ▼
    Compression
        │
        ▼
    Retention
        │
        ▼
    Removal When Retention Limit Is Reached

For the current rsyslog implementation:

    router.log
        │
        │ daily
        ▼
    router.log-YYYY-MM-DD
        │
        │ next rotation
        ▼
    router.log-YYYY-MM-DD.gz

The active `router.log` remains available for the application while older logs are retained as historical files.

## Configuration Locations

The primary system configuration is typically:

    /etc/logrotate.conf

Application-specific configurations are commonly stored under:

    /etc/logrotate.d/

The rsyslog Docker deployment uses:

    /etc/logrotate.d/rsyslog-docker

This keeps the application's rotation policy separate from the main system configuration.

## rsyslog Rotation Configuration

The centralized rsyslog collector writes persistent logs to a bind-mounted host directory.

Example active log:

    /opt/docker/rsyslog/logs/router.log

The host manages this file using:

    /etc/logrotate.d/rsyslog-docker

Configuration:

    /opt/docker/rsyslog/logs/router.log {
        daily
        rotate 90
        dateext
        dateformat -%Y-%m-%d
        compress
        delaycompress
        missingok
        notifempty
        copytruncate
    }

> [!note]
> This is a static example. Reference the active host configuration for the current homelab value.

## Rotation Policy

### `daily`

    daily

Makes the log eligible for rotation once per day.

The actual execution time is determined by the system's logrotate scheduler.

### `rotate`

    rotate 90

Retains up to 90 rotated log files before the oldest files are removed.

With daily rotation, this provides approximately 90 days of local history.

The number represents rotated files rather than an explicit number of days.

### `dateext`

    dateext

Uses a date suffix instead of numbered rotations.

Without `dateext`, files may look like:

    router.log.1
    router.log.2
    router.log.3

With `dateext`:

    router.log-2026-09-25
    router.log-2026-09-24.gz
    router.log-2026-09-23.gz

Date-based filenames make it easier to associate logs with incidents.

### `dateformat`

    dateformat -%Y-%m-%d

Defines the date suffix used with `dateext`.

The resulting format is:

    -YYYY-MM-DD

For example:

    router.log-2026-09-25

### `compress`

    compress

Compresses older rotated logs using gzip.

Compressed files use the `.gz` extension:

    router.log-2026-09-24.gz

Compression significantly reduces storage requirements for historical text logs.

### `delaycompress`

    delaycompress

Delays compression of the newest rotated file until the next rotation cycle.

Example:

    router.log
    router.log-2026-09-27
    router.log-2026-09-26.gz
    router.log-2026-09-25.gz

The newest rotated file remains directly readable without decompression until the next rotation.

`delaycompress` is used together with:

    compress

### `missingok`

    missingok

Prevents `logrotate` from treating a missing log file as an error.

This is useful when a service has not yet created its log or when the log may temporarily be absent.

### `notifempty`

    notifempty

Prevents rotation when the active log file is empty.

This avoids creating unnecessary empty historical files.

### `copytruncate`

    copytruncate

Copies the active log to the rotated filename and then truncates the original file in place.

Conceptually:

    router.log
        │
        ├── copy ─────► router.log-YYYY-MM-DD
        │
        └── truncate ─► router.log

The active file itself remains in place.

The application can therefore continue writing through its existing open file descriptor without reopening the log.

## Why `copytruncate` Is Used

The centralized rsyslog deployment runs inside a Docker container while `logrotate` runs directly on the host.

An initial rotation strategy renamed the active file:

    router.log
        │
        └── rename ──► router.log-YYYY-MM-DD

The rsyslog container was then sent a HUP signal so the daemon would reopen its log file.

During testing, the containerized rsyslog process did not recreate the active file as expected after receiving the signal.

Restarting the container recreated the active log, but restarting the logging service every day solely for rotation was undesirable.

The deployment therefore uses:

    copytruncate

Testing confirmed that:

- The rotated file was created
- The original active file remained present
- The original file was truncated
- New messages immediately continued appearing
- The rsyslog container did not restart
- No rsyslog errors were generated during rotation

> [!warning]
> `copytruncate` has a small race window between copying and truncating the active file. Messages written during that interval could theoretically be lost. This tradeoff is acceptable for the current homelab implementation.

## Testing a Configuration

Use debug mode before forcing a rotation:

    sudo logrotate -d /etc/logrotate.d/rsyslog-docker

Debug mode evaluates the configuration and reports what `logrotate` would do without actually modifying the log files.

Use this after changing a rotation configuration to check for syntax or policy problems.

## Forcing a Rotation

Force rotation regardless of whether the normal rotation criteria have been met:

    sudo logrotate -f /etc/logrotate.d/rsyslog-docker

For verbose output:

    sudo logrotate -vf /etc/logrotate.d/rsyslog-docker

A successful `copytruncate` rotation should include operations similar to:

    copying <ACTIVE-LOG> to <ROTATED-LOG>
    truncating <ACTIVE-LOG>

Afterward, inspect the directory:

    ls -lh /opt/docker/rsyslog/logs/

Expected:

    router.log
    router.log-YYYY-MM-DD

The active log should remain present but be much smaller immediately after rotation.

## Verify Continued Logging

After forcing a rotation, follow the active file:

    tail -f /opt/docker/rsyslog/logs/router.log

New messages should continue appearing without restarting the application.

For the rsyslog deployment, the container start timestamp can also be checked:

    docker inspect -f '{{.State.StartedAt}}' rsyslog

The timestamp should remain unchanged after a normal `copytruncate` rotation.

Check the application for errors:

    docker logs rsyslog --since 5m

## Automatic Rotation

On systems using systemd, automatic log rotation is typically scheduled through:

    logrotate.timer

Check its status:

    systemctl status logrotate.timer

A functioning timer should report:

    Active: active (waiting)

Display the next scheduled execution:

    systemctl list-timers logrotate.timer

The timer triggers:

    logrotate.service

The service processes the system's logrotate configuration, including application-specific files under:

    /etc/logrotate.d/

A separate cron job is not required when the systemd timer is active.

## Check logrotate Service History

View the most recent service status:

    systemctl status logrotate.service

View service journal entries:

    journalctl -u logrotate.service

Show recent entries:

    journalctl -u logrotate.service -n 50

Show entries from the current boot:

    journalctl -u logrotate.service -b

These commands are useful when an expected automatic rotation did not occur.

## Reading Rotated Logs

List the log directory:

    ls -lh /opt/docker/rsyslog/logs/

A directory using the current policy may contain:

    router.log
    router.log-2026-09-27
    router.log-2026-09-26.gz
    router.log-2026-09-25.gz

### Read the Newest Rotated Log

If `delaycompress` is enabled, the newest rotation is normally uncompressed:

    less /opt/docker/rsyslog/logs/router.log-YYYY-MM-DD

### Read a Compressed Log

Use:

    zless /opt/docker/rsyslog/logs/router.log-YYYY-MM-DD.gz

### Search a Compressed Log

Use:

    zgrep -i "wan" /opt/docker/rsyslog/logs/router.log-YYYY-MM-DD.gz

### Search Multiple Historical Logs

Example:

    zgrep -i "wan" /opt/docker/rsyslog/logs/router.log-*.gz

For multiple patterns:

    zgrep -Ei "wan|link|reboot|watchdog|error|fail" \
        /opt/docker/rsyslog/logs/router.log-*.gz

## File Ownership

`copytruncate` is useful when ownership and open file descriptors need to remain unchanged.

Because the active file is truncated rather than replaced, its existing ownership and permissions remain intact.

Check:

    ls -l /opt/docker/rsyslog/logs/

If an application runs under a specific container UID/GID, retaining the original active file can avoid permission problems that might occur if a newly created file has different ownership.

## Troubleshooting

### Log Does Not Rotate

Check the configuration:

    sudo logrotate -d /etc/logrotate.d/rsyslog-docker

If the output reports that the log does not need rotating, the normal rotation criteria have not yet been met.

Force a test if necessary:

    sudo logrotate -vf /etc/logrotate.d/rsyslog-docker

### Rotation Already Occurred Today

`logrotate` maintains state about previous rotations.

A daily policy normally prevents the same log from rotating repeatedly during the same day.

For testing, override the normal decision with:

    sudo logrotate -vf /etc/logrotate.d/rsyslog-docker

Use forced rotation for testing rather than normal operation.

### Active Log Disappears

With the current `copytruncate` configuration, the active log should remain present.

Check:

    ls -lh /opt/docker/rsyslog/logs/

Confirm the configuration contains:

    copytruncate

If a previous configuration used `postrotate`, `create`, or application signaling, confirm those directives are no longer unintentionally present.

### Application Stops Writing After Rotation

Check the active file:

    ls -l /opt/docker/rsyslog/logs/router.log

Follow it:

    tail -f /opt/docker/rsyslog/logs/router.log

Check the application:

    docker logs rsyslog

With `copytruncate`, the application should continue writing through the same open file descriptor.

### Rotated Logs Are Not Compressed

With:

    compress
    delaycompress

the newest rotated file is intentionally left uncompressed.

For example:

    router.log
    router.log-2026-09-27
    router.log-2026-09-26.gz

The newest rotated file should be compressed during the following rotation.

### Automatic Rotation Does Not Run

Check the timer:

    systemctl status logrotate.timer

Check the next execution:

    systemctl list-timers logrotate.timer

Check the service:

    systemctl status logrotate.service

Review its journal:

    journalctl -u logrotate.service

## Operational Checklist

After creating a new logrotate configuration:

    1. Verify the target log path.
    2. Confirm the desired rotation frequency.
    3. Set the retention count.
    4. Configure compression if appropriate.
    5. Determine whether the application supports reopening logs.
    6. Use copytruncate only when appropriate.
    7. Run logrotate in debug mode.
    8. Force one test rotation.
    9. Verify the rotated file.
    10. Verify the application continues writing.
    11. Confirm logrotate.timer is active.

## Current rsyslog Policy

The centralized rsyslog deployment currently uses:

    Frequency:        Daily
    Retention:        90 rotations
    Date filenames:   Enabled
    Compression:      Enabled
    Delay compression: Enabled
    Empty log skip:   Enabled
    Missing log skip: Enabled
    Rotation method:  copytruncate

Expected lifecycle:

    router.log
        │
        ▼
    router.log-YYYY-MM-DD
        │
        ▼
    router.log-YYYY-MM-DD.gz
        │
        ▼
    Removed after retention limit

The host manages rotation independently from the containerized logging service.
