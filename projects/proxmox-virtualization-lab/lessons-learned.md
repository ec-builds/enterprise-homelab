# Proxmox Lessons Learned

Operational lessons identified while building, testing, and maintaining the Proxmox environment.

| Date | Summary | Context | Takeaway |
|---|---|---|---|
| 2026-10-01 | **Redundant Services Prevented VM Migration from Becoming a Network Outage** | During node evacuation, `adguard-lab-02` was migrated to another Proxmox node and was temporarily unavailable during the migration. A second AdGuard DNS instance, `adguard-lab-01`, remained online on another node and continued servicing DNS requests. Network clients therefore remained operational while the VM was unavailable. | Redundancy at the service layer can prevent planned VM downtime from becoming a service outage. Critical infrastructure should use multiple instances distributed across separate virtualization hosts where practical. This allows maintenance or failure of an individual VM or hypervisor without necessarily interrupting the underlying service. |
| 2026-10-01 | **VM Migration Requires Planned Downtime** | VMs were migrated between Proxmox nodes while evacuating a node for hardware changes. Because the environment uses node-local storage, VM disks had to be transferred across the network to storage on the destination nodes. One measured VM migration resulted in approximately **12 minutes of downtime** before the workload was available on the destination node. | Migration time must be considered when planning maintenance involving node-local storage. Moving a VM between cluster nodes is not necessarily an instantaneous failover when its virtual disks must also be transferred. Migration duration depends on VM disk size, network throughput, storage performance, migration method, and concurrent transfers. Future maintenance should account for an appropriate outage window and include post-migration workload verification. |
| 2026-09-01 | **Node-Local Storage Required CLI-Based VM Migration** | A VM needed to be migrated between Proxmox cluster nodes using separate node-local NVMe storage. The GUI migration failed because the source storage was not available on the destination node and could not be automatically mapped to the destination storage pool. The VM was instead migrated using the CLI with explicit destination-storage mapping and subsequently verified on the destination node. | Proxmox clustering does not make node-local storage shared between hosts. When the GUI cannot map local storage during migration, the CLI can explicitly specify the destination storage. See the **Proxmox CLI VM Migration** reference documentation for the migration procedure. |
| 2026-08-31 | **DHCP Addressing Prevented Proxmox Cluster Configuration** | The Proxmox management bridge (`vmbr0`) was initially configured using DHCP. Although the node consistently received the expected address through a DHCP reservation, Proxmox did not present the dynamically assigned address as an available Corosync cluster link during cluster creation. The management interface was changed from DHCP to a static address directly within Proxmox. Stale hostname resolution was also corrected and validated using `hostname -I` and `getent hosts`. | A DHCP reservation provides predictable addressing from the DHCP server, but the host still considers the address dynamically assigned. Cluster infrastructure benefits from static host-level addressing to provide stable management and Corosync endpoints. Network configuration, hostname resolution, and management-IP consistency should therefore be validated before initializing a Proxmox cluster. |
| 2026-08-31 | **Recreated LVM-Thin Storage for Standardized Cluster Naming** | After adding a Proxmox node to the cluster, its secondary NVMe device was detected by Linux and remained configured as an LVM thin pool, but its storage entry did not appear alongside the node's other Proxmox storage. Investigation showed that the underlying LVM storage and the Proxmox storage definition were separate configuration layers. Because the environment was still being built and the thin pool contained no VM data, the additional storage was removed and recreated using a consistent node-based naming convention. | Removing a storage entry from **Datacenter → Storage** removes the Proxmox storage definition but does not remove the underlying LVM volume group, thin pool, or physical-volume metadata. `pvesm`, `pvs`, `vgs`, and `lvs` help distinguish between the Proxmox storage layer and the underlying Linux LVM configuration. Storage naming should ideally be standardized before workloads are deployed because changing storage identifiers becomes more complicated once VM or container disks reference them. |
| 2026-08-15 | **Nested KVM Caused CPU Soft Lockups in VMware** | While testing Proxmox VE inside VMware Workstation, nested VT-x/EPT was enabled so Proxmox could run KVM virtual machines. This caused repeated CPU soft lockups and eventually made the Proxmox VM unstable, including `watchdog: BUG: soft lockup - CPU#2 stuck for 22s! [CPU 0/KVM]`. Disabling nested VT-x/EPT immediately stabilized the Proxmox VM. | Nested virtualization adds another hypervisor layer and can introduce stability issues that are not present with bare-metal virtualization. The successful test without nested VT-x/EPT isolated the issue to the **VMware → Proxmox → KVM** virtualization path rather than Proxmox itself. Nested environments are useful for management and configuration testing but should not automatically be treated as representative of bare-metal hypervisor behavior. |
| 2026-08-15 | **Hyper-V and VBS Can Prevent VMware Nested Virtualization** | VMware initially reported that Hyper-V or Device/Credential Guard was active and that nested virtualization was unavailable. Disabling Hyper-V alone did not resolve the issue because Windows Virtualization-Based Security (VBS) remained active. `msinfo32` confirmed VBS was still running. Hyper-V, Memory Integrity, unnecessary Windows virtualization components, and VBS were subsequently disabled, including **Turn On Virtualization Based Security** through Group Policy. | Disabling the Hyper-V Windows Feature does not necessarily stop the Microsoft hypervisor. VBS and Memory Integrity/HVCI can continue using the virtualization layer. Troubleshooting nested virtualization therefore requires distinguishing **hardware virtualization (VT-x/EPT)** from the **Windows hypervisor/VBS layer** and verifying the actual system state rather than relying solely on installed Windows Features. |
