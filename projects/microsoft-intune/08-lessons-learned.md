# Lessons Learned

| Date | Summary | Context | Takeaway |
|---|---|---|---|
| 2026-10-08 | **Intune Compliance Evaluates Individual Security Requirements Independently** | `WIN11-CLIENT-02` was marked Noncompliant even though most security requirements passed. Per-setting results identified BitLocker, storage encryption, and minimum OS version as the failed requirements. | Use per-setting compliance results to identify the controls responsible for an overall Noncompliant state. |
| 2026-10-08 | **Minimum OS Version Requires a Properly Formatted Version Baseline** | The policy initially used `26200` even though the endpoint was running build `26200`. Updating the requirement to `10.0.26200.0` allowed Intune to evaluate the intended baseline correctly. | Validate both the endpoint version and compliance-policy version format when an OS requirement fails unexpectedly. |
| 2026-10-08 | **Compliance Failures Should Be Remediated Rather Than Weakening the Baseline** | BitLocker and storage encryption initially failed compliance. BitLocker was enabled, the drive encrypted, and the recovery key backed up to Microsoft Entra ID. After remediation and an Intune sync, the device became Compliant. | Remediate the endpoint before weakening a valid security requirement. |
| 2026-10-07 | **Intune Enrollment Restrictions Control Device Eligibility, Not Administrative Permission** | The default All Users restriction was hardened to allow Windows MDM while blocking unsupported platforms and personally owned Windows devices. Testing confirmed that these restrictions control enrollment eligibility rather than Intune administrative access. | Use enrollment restrictions for device eligibility and Intune RBAC for administrative authorization. |
| 2026-10-07 | **Manual Windows MDM Enrollment Was Classified as Personal** | A Microsoft Entra joined device enrolled through **Enroll only in device management** was classified as Personal. Blocking personally owned Windows devices caused enrollment error `0x80180014`; allowing them permitted the same enrollment to succeed. | Entra join, Intune management, and Intune ownership are separate device properties. |
| 2026-10-07 | **Enrollment Restrictions Should Be Validated Through Controlled Testing** | Blocking personally owned Windows devices caused enrollment to fail. Temporarily allowing them enabled the same endpoint and user to enroll successfully, confirming that the restriction caused the failure. | Change one relevant variable at a time to validate security-control behavior. |
| 2026-10-07 | **Local Windows Privileges and Intune Cloud Permissions Are Separate** | Manual enrollment failed from a standard Windows session even with tenant administrator credentials. From a local Administrator session, enrollment succeeded using the regular organizational `user1` account. | Treat local Windows privileges, organizational authentication, and Intune RBAC as separate security contexts. |
| 2026-10-07 | **Microsoft Entra Join and Intune Enrollment Are Separate Device States** | The endpoint was first joined to Microsoft Entra ID and later enrolled separately into Intune. Windows and Intune then independently reported its identity, management, ownership, and compliance states. | Verify device identity and MDM enrollment independently when provisioning or troubleshooting endpoints. |
| 2026-10-07 | **Corporate Ownership Requires a Deliberate Enrollment Strategy** | Manual MDM enrollment classified the test endpoint as Personal, conflicting with the goal of blocking personally owned Windows devices. A corporate provisioning method such as Windows Autopilot will be evaluated later. | Establish a repeatable corporate enrollment method before permanently blocking personal-device enrollment. |
| 2026-08-13 | **Intune RBAC Uses Group-Based Scoped Assignments** | An Intune Application Manager assignment used an administrative group for role membership and dedicated scope groups for the users and devices those administrators could manage. | Intune roles define **what** administrators can do; assignments and scopes define **who** receives access and **where** it applies. |
| 2026-08-13 | **Entra and Intune Use Separate RBAC Systems** | Testing showed that tenant and directory roles such as Intune Administrator are managed through Microsoft Entra, while granular endpoint roles such as Application Manager are provided through Intune RBAC. | Identify which RBAC system owns a permission before assigning administrative access. |
