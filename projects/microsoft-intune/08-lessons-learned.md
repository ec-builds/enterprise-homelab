# Lessons Learned


| Date | Summary | Context | Takeaway |
|---|---|---|---|
| 2026-10-07 | **Intune Enrollment Restrictions Control Device Eligibility, Not Administrative Permission** | While configuring Windows enrollment restrictions, the default **All Users** platform restriction was hardened to allow Windows MDM while blocking unsupported platforms and personally owned Windows devices. Testing showed that assigning enrollment restrictions determines which device platforms, ownership types, and other device characteristics are permitted to enroll; it does not grant a user permission to administer Intune or function as a direct user enrollment allow-list. | Separate **enrollment restrictions** from administrative authorization. Enrollment restrictions define which devices are eligible for enrollment, while Intune RBAC controls administrative capabilities. These mechanisms should be designed independently rather than treating an enrollment restriction assignment as an administrative permission. |
| 2026-10-07 | **Manual Windows MDM Enrollment Was Classified as Personal** | A Microsoft Entra joined Windows test device was manually enrolled using the Windows **Enroll only in device management** workflow. With personally owned Windows enrollment blocked, Intune rejected the enrollment with error `0x80180014`. Personally owned enrollment was temporarily allowed and the same enrollment subsequently succeeded. The device inventory then showed **Managed by: Intune**, **Ownership: Personal**, and **Compliance: Compliant**, confirming how Intune classified the enrollment. | Microsoft Entra join state, Intune management state, and Intune ownership classification are separate properties. An Entra joined device can still appear as **Personal** in Intune when the enrollment method does not provide the expected corporate ownership signal. A corporate-owned provisioning workflow should therefore be established before enforcing a policy that blocks all personally owned Windows enrollment. |
| 2026-10-07 | **Enrollment Restrictions Should Be Validated Through Controlled Testing** | Blocking personally owned Windows devices produced an enrollment failure. The restriction was temporarily changed to allow personal Windows enrollment, after which the same user and endpoint successfully completed enrollment. Intune subsequently reported the endpoint as Personal, directly correlating the restriction with the failed enrollment attempt. | Security controls should be validated by changing one relevant variable and repeating the same test. Temporarily relaxing the ownership restriction established a known comparison and demonstrated that the policy was actually enforcing the intended behavior rather than assuming the Windows error message accurately identified the underlying cause. |
| 2026-10-07 | **Local Windows Privileges and Intune Cloud Permissions Are Separate** | Manual enrollment initially failed when attempted from a standard Windows user session, even when tenant administrator credentials were supplied. After signing into a local Administrator profile, the enrollment workflow could be initiated successfully using the regular organizational `user1` account. This showed that the Windows session's local privileges and the organizational identity supplied during enrollment serve different purposes. | Local Windows authorization, organizational user authentication, and Intune administrative RBAC should be treated as separate security contexts. Granting a user the Intune Administrator role does not provide local Windows elevation, and normal users should not receive Intune administrative privileges simply to enroll an endpoint. |
| 2026-10-07 | **Microsoft Entra Join and Intune Enrollment Are Separate Device States** | The Windows test endpoint was connected to Microsoft Entra ID and later enrolled separately into Intune MDM. After successful enrollment, Windows displayed both an Entra ID connection and an EC-Builds MDM connection. Intune independently reported the endpoint as managed, compliant, and Personal. | Device identity and device management should not be treated as the same operation. Microsoft Entra establishes the device's cloud identity and join state, while Microsoft Intune provides MDM management, policy, compliance, application, and lifecycle capabilities. Troubleshooting should verify both states independently. |
| 2026-10-07 | **Corporate Ownership Requires a Deliberate Enrollment Strategy** | The lab's desired security posture is to allow organization-managed Windows devices while blocking personally owned Windows enrollment. Testing demonstrated that the current manual MDM enrollment workflow results in Personal ownership, preventing enrollment when the personal-device restriction is enforced. A future corporate enrollment method, including evaluation of Windows Autopilot, is therefore required before the desired restriction can remain enforced without preventing legitimate device provisioning. | Device ownership should be incorporated into the provisioning design rather than corrected only after enrollment. Establishing a repeatable corporate-device enrollment workflow will allow personally owned enrollment to remain blocked while still permitting approved organization-owned Windows endpoints to enter management. |
| 2026-08-13 | **Intune RBAC Uses Group-Based Scoped Assignments** | While assigning the Intune Application Manager role, Intune permissions were found to be assigned through role assignments rather than directly to individual administrators. A role assignment connects an Intune role to an administrative group and defines the users and devices that group is permitted to manage. An `Intune-App-Admins` security group was created for delegated application administration, with management scoped to dedicated `Intune-Lab-Users` and `Intune-Lab-Devices` groups. | An Intune role defines **what** an administrator can do, while the role assignment determines **who** receives those permissions and **where** they apply. Admin Groups identify the administrators, Scope Groups define the users and devices they can manage, and Scope Tags can further restrict accessible Intune resources. Each role requires its own assignment, while administrative and scope groups can be reused. Permissions from multiple assignments are cumulative and should therefore be scoped carefully. |
| 2026-08-13 | **Entra and Intune Use Separate RBAC Systems** | During initial tenant configuration, Microsoft documentation presented Entra administrative roles and Intune-specific roles together. Searching Microsoft Entra ID for Application Manager instead returned Application Administrator, initially making the role structure unclear. Further configuration showed that roles such as Intune Administrator, User Administrator, and Domain Name Administrator belong to Microsoft Entra, while Application Manager, Intune Role Administrator, and Policy and Profile Manager are configured through Intune RBAC. | Microsoft Entra and Microsoft Intune maintain separate RBAC systems. Entra roles provide directory and tenant-level administrative permissions, while Intune roles provide granular permissions over endpoint-management functions. Similarly named roles across the two systems are not necessarily interchangeable, so administrators should identify which RBAC system owns a permission before assigning access. |
