# Docker Lab — Lessons Learned

A running log of decisions and best practices from building the Docker & Self-Hosted Services project.

| # | Topic | Decision | Why |
|---|-------|----------|-----|
| 001 | Docker project directory | Store Compose stacks in `/opt/docker`, one directory per stack (on Linux hosts) | `/opt` is the Linux convention for optional/third-party software — keeps self-hosted services separate from personal files (`/home`) and is easy to reproduce across servers. Compose location doesn't affect containers (data lives in `/var/lib/docker`); consistency matters more than the path. |
| 002 | Uptime Kuma database | Embedded MariaDB | Production-grade without running a separate DB service, and more scalable than SQLite — a good fit for small-to-medium homelab monitoring. Revisit if monitoring needs grow. |
| 003 | Container naming | Set `container_name` explicitly (e.g. `uptime-kuma`) | Shorter, readable names simplify logs, restarts, and troubleshooting vs. auto-generated names like `uptime-kuma-uptime-kuma-1`. Names must be unique per host, so remove an existing container before recreating it. |
| 004 | Docker host separation | Separate workloads by operational role across dedicated Docker VMs: `docker-lab` for general self-hosted applications, `monitor-lab` for monitoring and observability, and `media-lab` for persistent media services | Separating workloads limits the impact of maintenance, testing, and failures. Lab changes can occur without disrupting monitoring or household media services, while each host can be managed, backed up, and recovered independently. |
| 005 | Container management | Use Portainer for container administration | Provides a web UI for managing containers, images, volumes, networks, and Compose stacks — faster visibility and control than CLI-only for day-to-day operations, without replacing Compose for deployment. |
| 006 | Monitoring fault isolation | Run monitoring and observability services on `monitor-lab` rather than the primary `docker-lab` host | Monitoring is most useful when it remains available during failures. Hosting Uptime Kuma, Prometheus, Grafana, and Loki separately allows the monitoring stack to observe outages or maintenance affecting the primary Docker host instead of disappearing with it. |
| 007 | Media service isolation | Run Jellyfin on a dedicated `media-lab` Docker VM rather than alongside general lab workloads | Jellyfin is a persistent household service rather than an experimental lab workload. Isolating it allows Docker experimentation and maintenance elsewhere without interrupting media access, while providing a dedicated lifecycle for backups, resource allocation, and future hardware acceleration. |
| 008 | Debian VM standardization | Deploy Docker hosts from a common Debian template and apply the same baseline before workload-specific configuration | A standardized starting point reduces configuration drift and makes Docker hosts easier to reproduce, troubleshoot, and replace. Workload-specific configuration begins only after the common operating system baseline is validated. |
| 009 | VM clone identity | Clear machine-specific identity from the Debian template and verify that each clone receives its own machine ID and SSH host keys | Cloned systems must have unique identities. Machine IDs regenerate on first boot, while missing SSH host keys may require `ssh-keygen -A`; validating both prevents duplicate identity and SSH trust issues between cloned VMs. |
| 010 | Documentation scope | Keep architecture decisions in project documentation and reusable deployment procedures in shared reference documentation | Separating project-specific design from reusable procedures reduces duplication. The project documents what is deployed and why, while Debian, Docker, and virtualization references document repeatable implementation procedures. |
