# 🔧 Troubleshooting

Issues encountered while building, configuring, and testing the Proxmox environment.

| Issue | Symptom | Cause | Resolution | Impact / Lesson Learned |
|---|---|---|---|---|
| **Node-Local NVMe Storage Unavailable After Joining Cluster** | After joining a second Proxmox host to the cluster, its secondary NVMe remained present at the Linux and LVM layers but did not initially appear as usable storage in the Proxmox resource tree. | Proxmox storage definitions are managed through cluster configuration, while the underlying physical volumes, volume groups, and thin pools remain local to each node. | Verified the storage with `pvesm status`, `pvs`, `vgs`, and `lvs`, then reconfigured the NVMe storage in Proxmox using standardized node-specific storage IDs such as `nvme-01-lvm`, `nvme-02-lvm`, and `nvme-03-lvm`. | Proxmox storage configuration and the underlying Linux storage stack are separate layers. Verify the disk and LVM configuration before recreating, formatting, or otherwise modifying storage that disappears from the Proxmox interface. |
| **Proxmox Management Address Persisted After Switching to DHCP** | After changing `vmbr0` from static addressing to DHCP, the bridge temporarily showed both the original static IP and a DHCP-assigned IP. The boot console also continued displaying the old management address. | The installation-time static configuration remained associated with `vmbr0`, while the old address was still mapped to the Proxmox hostname in `/etc/hosts`. | Changed `vmbr0` to DHCP and updated `/etc/hosts` to reflect the current management address. | The host returned to a single management address and the console displayed the correct management URL after reboot. Network configuration and hostname resolution should be checked together when changing Proxmox management addressing. |
| **Windows Boot Manager Prevented Proxmox Boot** | After the bare-metal Proxmox installation, the system did not automatically boot into Proxmox. | Dell UEFI firmware retained and prioritized a Windows Boot Manager entry from the system's previous Windows installation. | Disabled Windows Boot Manager in the BIOS/UEFI boot configuration while retaining UEFI boot mode. | Proxmox booted normally without installation media. The issue was isolated to firmware boot configuration rather than the Proxmox installation. |
| **VMware Nested Virtualization Unavailable** | VMware reported that nested virtualization was unavailable because Hyper-V or Device/Credential Guard was active. | Windows Virtualization-Based Security remained active even after the Hyper-V Windows Feature was disabled. | Disabled VBS and verified through `msinfo32` that the Microsoft hypervisor was no longer active. | Disabling the Hyper-V feature alone does not necessarily disable the Windows virtualization layer. VBS and related security features must also be considered when troubleshooting nested virtualization. |
| **Proxmox CPU Soft Lockups Under Nested KVM** | Proxmox repeatedly reported `watchdog: BUG: soft lockup - CPU#2 stuck for 22s! [CPU 0/KVM]` while running as a VMware VM with nested virtualization enabled. | Instability occurred when VMware exposed nested VT-x/EPT to the virtualized Proxmox environment. | Disabled VMware nested virtualization and confirmed that the Proxmox VM remained stable. | The successful test without nested VT-x/EPT isolated the instability to the nested **VMware → Proxmox → KVM** virtualization path. Nested environments are useful for testing but should not automatically be considered representative of bare-metal behavior. |
