# Lessons Learned

| Date | Lesson | Key Takeaway |
|---|---|---|
| 2026-09-11 | **Keep the Previous Service Available During Cutover** | The original Jellyfin service was stopped but left intact while the replacement was deployed and tested. Keeping the previous environment available for several days provides a practical rollback path if unexpected problems appear. The old service can be retired after the replacement has passed functional testing and demonstrated stable operation. |
| 2026-09-11 | **Migration Is Not Always Better Than a Clean Deployment** | When moving between substantially different architectures, preserving an existing installation may introduce more complexity than value. Because the meaningful loss in moving from native Jellyfin to Docker was limited primarily to watch history and recreating users, deploying a clean instance was simpler than migrating the existing database and configuration. |
| 2026-09-11 | **Persistent Data Should Be Independent of Containers** | Docker bind mounts were selected for Jellyfin configuration and cache storage so application data remains outside the container lifecycle. Containers can therefore be recreated or replaced while persistent data remains accessible and straightforward to inspect, back up, and migrate. |
| 2026-09-11 | **Architecture Should Be Allowed to Evolve** | The original native deployment was not a mistake simply because the platform later moved to Proxmox and Docker. It met the original project's objectives and provided foundational Linux experience. Modernizing it later demonstrated how infrastructure can evolve as requirements, skills, and platform standards change. |
| | **Linux Administration Is Learned Through Repetition** | Linux concepts became significantly easier through repeated practical use. Navigating the filesystem, managing systemd services, editing configuration files, installing packages, and validating system state became more intuitive through hands-on administration rather than study alone. |
| | **Documentation Is Part of the Project** | Documentation is not separate from infrastructure work. Maintaining procedures during the build created repeatable deployments, simplified troubleshooting, improved architectural understanding, and provided a recovery reference. |
| | **Service Accounts Improve Security** | A dedicated read-only service account was used for media storage access rather than an administrative storage account. This reduced privileges, improved separation of responsibilities, simplified auditing, and reinforced the principle of least privilege. |
| | **Storage and Applications Should Be Separated** | Media content remained on centralized network storage while Jellyfin provided the application layer. Separating application state from media storage simplified deployment, recovery, and migration while reducing the risk of accidental changes to source media. |
| | **Container Formats and Codecs Are Different** | Troubleshooting playback quality demonstrated that container formats such as MKV and MP4 do not determine media quality or compatibility by themselves. Video and audio codecs determine whether clients can direct play content or require transcoding. |
| | **Validation Is as Important as Deployment** | A successful installation does not necessarily mean a service is operational. Browser and streaming-client access, network connectivity, restart behavior, storage access, and recovery scenarios all required validation before the platform could be considered reliable. |
| | **Existing Hardware Is Often Good Enough** | The original platform successfully ran on repurposed hardware with modest resources. This demonstrated that learning Linux administration, storage integration, networking, and self-hosted services does not require enterprise-grade equipment. |
| | **Understanding the Commands Matters** | Following installation documentation can produce a working system, but understanding the commands provides greater long-term value. Repository configuration introduced environment variables, command substitution, redirection, package repositories, signing keys, and trust relationships. |
| | **Small Projects Build Foundational Skills** | A relatively simple media platform introduced concepts used throughout larger infrastructure environments, including operating system deployment, package management, services, storage, permissions, security, documentation, and structured troubleshooting. |
